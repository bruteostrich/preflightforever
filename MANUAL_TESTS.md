# In-game acceptance checks

These checks require the actual Forever client. They are not claimed as completed by the mocked test suite.

1. Install the ZIP in `_forever_/Interface/AddOns`, start the client, and enable Preflight Forever. Run `/console scriptErrors 1` to make any Lua errors visible.
2. Outdoors before visiting a flight master, open `/pf`. With existing schema-2 Dungeon Journal records, only those confirmed points should be selectable; unsupported remote positives stay red/unverified, even if the API reports every point known. Without either journal or native records, the known list should remain empty with synchronization guidance. Confirm the named source is the closest faction-compatible point, known or not, and that an undiscovered one is labeled "(undiscovered)". Queue a known destination from an undiscovered closest point, then talk to that flight master: it should be discovered and the queued flight should depart. Check Eastern Kingdoms and Kalimdor, both factions, and neutral points. Opposing-faction points must not appear. Upgrade a 0.2.2 save containing false-positive learned entries; those must not restore an unverified queue or unlock points.
3. Compare the displayed nearest point to your position. If pins appear displaced, capture the map name, zone, `/dump GetBuildInfo()`, and `/dump C_Map.GetBestMapForUnit("player")`. No exact NPC walking-route distance is promised.
4. Drag the button and window, close with Escape, reopen, then `/reload`. Verify positions and automatic-departure preference persist. Use `/pf reset` to recover their default positions.
5. Visit a flight master without a queue. Open the taxi map, close it, and open Preflight Forever. Confirm both positive and negative corrections: a point the remote API marked known but the real map reports unavailable must become red/unselectable; one the native map confirms must become known even if its remote flag disagrees. Refresh and `/reload`; stale remote flags or Dungeon Journal entries must not overwrite those corrections. Visit again after learning a new point and confirm the new native observation can update the saved correction.
6. Queue a known destination while away from the NPC. Confirm no flight starts remotely. Return to the **named source** and open its taxi map. Expect exactly one departure to the queued destination and a cleared queue only once airborne. The normal fare is charged.
7. Repeat at an NPC with a gossip menu: automatic mode should choose only its single available flight-service option. If its menu is not recognized, manually choose the flight service; queue processing still runs when the taxi map opens.
8. Queue another flight and visit a different master. Expect no departure and the original queue retained. Hold Shift as you open the selected master's taxi map; expect no automatic departure and the queue retained.
9. Turn off automatic departure. Visit the selected master; expect the planner's **Depart now** button to become available without buying a flight. Click it to depart. Close the NPC map and verify that the button becomes unavailable.
10. Try an unavailable destination, a fare you cannot afford, a map-transition pin, and a special-service flight if the client exposes them. No automatic flight should start; the normal map remains usable.
11. Open and immediately close a flight map with a queue pending. No delayed departure should occur after the interaction closes. Replace or cancel a queue; confirm the old destination cannot trigger later.
12. Log into another character. Discovery, queue, and settings must be separate. Test alongside the installed UI addons, particularly ElvUI and Leatrix flight features.
13. Before any native visit, hover both a map pin and a destination row confirmed by existing journal records. Confirm arrows through the bundled connections and directional chevrons on the unobstructed map; the bottom panel should show the destination name, status, **Estimated route**, flight time, and timing source without opening a destination tooltip. Hover a red point and confirm the bottom panel explains unknown or unverified status. Then open the selected departure master's real map and hover again in Preflight Forever: the native cached route must replace the estimate. Compare every hop to the native hover route, including intermediate stops. Leave the pin/list row, close the window, or filter out the hovered row: its details and arrows must clear. Stand still through several refreshes: the active details and route must remain. Check a long route for overlap with the queue controls, and confirm the floating gryphon button still has its help tooltip.
14. Check an estimated database time before the first trip. Complete that exact flight (test both a normal native selection and a queued selection), return to the source, and hover again: the time source should now say **Recorded flight**. Test with and without Frequent Flier. Early landing, interrupted/reloaded flights, and changed routes must not overwrite the full route's timing.
15. Check the whole continent map on first opening and after several refreshes. The native sea/parchment background should fill transparent areas and no panel background should cover a tile. Allow streaming textures to finish loading. Run `/pf debug` if a black area persists; its tile counts and loading state are also saved in `PreflightDB.lastDiagnostics` for diagnosis.
16. Compare a bundled direct connection with the native map even where a shorter sequence through another known point exists. The preview should prefer the direct flight. Also compare several destinations that require intermediate stops from that source. After opening the native map, run `/pf debug` and check the matching/differing/unavailable estimate counts. A differing estimate must never replace the actual native route just captured. Record the source, destination, known intermediate points, build, and both stop sequences for any mismatch; an estimate match on one route does not establish all-route accuracy.
17. After recording a route, learn another flight point and synchronize your known list at a flight master. Recheck a previously visited departure: stale recorded routes should give way to a fresh estimate, or show **Previously recorded** when no estimate is available. Visiting that departure again must restore current native routing. Repeat after a client build change when practical. A measured duration should remain attached only to its matching stop sequence.
18. On a druid, distinguish the class-only Nighthaven services from ordinary flight masters. The bundled ordinary graph must not use the Nighthaven-to-Rut'theran or Nighthaven-to-Thunder-Bluff class service as a connecting shortcut. These services are excluded from the estimate data, not removed from the game.

If automatic selection is blocked by the client, select the destination manually on Blizzard's map. Preflight Forever retains the queue when it cannot confirm its requested departure; clear it with `/pf clear` if you complete the trip manually.
